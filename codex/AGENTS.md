# 通用工作原则与编码习惯

对所有项目生效的个人习惯与通用工程原则。特定技术栈的专属约定由下方的可选私有规则补充。
项目及子目录的 AGENTS.md 补充架构、业务约束和验证命令；代码风格优先遵循项目现有约定，下方个人习惯作为没有明确约定时的默认值，不为套用个人习惯重构已有代码。

> 下面 1-4 条源自 Andrej Karpathy 对 LLM 编码通病的总结，偏向「稳」而非「快」；琐碎任务（改错别字、明显的一行改动）自行把握，不必套全套。

## 1. 先想清楚再写
**先查证，再决策；只把影响结果的歧义交给用户。**

动手之前：
- 优先从代码、测试和项目文档确认事实；可逆的常规实现选择自主决定，必要时简述依据。
- 只有需求歧义会实质改变行为、兼容性或操作授权时才询问；等待回答时继续不依赖答案的工作。
- 有更简单的做法就说出来。该反对时反对。
- 用户已明确需求和边界后，自主完成理解、实现、测试和修复，不在每个阶段重复请求确认；用户明确要求先审批方案时遵守。

## 2. 简单优先
**用解决问题所需的最少代码。不写任何投机性的东西。**

- 不做没要求的功能。
- 不为只用一次的代码做抽象。
- 少量重复可以保留；只有多处逻辑表达同一个业务概念或稳定规则，且提取后调用方更清楚时才抽象，不因代码外形相似就合并。
- 不加没人要求的「灵活性」和「可配置」。
- 不为不可能发生的情况写错误处理。
- 本次新增代码写了 200 行但 50 行能搞定，就简化；不要借此重写已有模块。

自问：「资深工程师会不会觉得这写复杂了？」会，就简化。

## 3. 外科式改动
**只碰必须碰的。只收拾自己弄出的烂摊子。**

- 不「顺手改进」旁边的代码、注释或格式；没坏的东西不要重构。
- 优先在现有函数和模块内解决问题；不为小功能拆文件、换架构或批量改名，确需扩大范围时先说明必要性和影响。
- 沿用项目现有风格，局部修改保留周边代码的布局和格式，不顺带统一其他代码。
- 看到无关的死代码，提出来，不要删。
- 只删除因你的改动而变得没用的 import / 变量 / 函数；不要动本来就存在的死代码，除非被要求。
- 检验标准：每一行改动都能直接追溯到用户的要求。
- 改动的连带影响：修改共享工具函数的返回结构（加字段/改名/语义变化）时，先搜索所有 caller，逐个确认兼容性并同步受影响的调用；只传递调用方需要的字段，不为自动透传改成全量展开。

## 4. 目标驱动
**先定验收标准，然后循环到验证通过为止。**

把任务变成可验证的目标：
- 「加校验」→「为非法输入写测试，然后让它们通过」
- 「修 bug」→「写一个能复现的测试，然后让它通过」
- 「重构 X」→「确保重构前后测试都通过」

多步任务先给一段简短计划（每步带验证）：
```
1. [步骤] → 验证：[检查方式]
2. [步骤] → 验证：[检查方式]
```
验收标准够硬，你才能自己循环推进；标准含糊（「让它能跑」）就只能反复来问。

## 验证与审查

- 先确认项目现有的运行、测试和静态检查入口，再选择与改动范围匹配的检查。
- 修复行为缺陷时，优先增加能复现问题的回归测试；纯文案、格式或配置小改动使用相应静态检查，不为形式补测试。
- 检查失败先定位并修复改动引入的问题；已有失败或环境限制要明确记录，不能宣称验证通过。
- 验证通过后检查最终 diff、相关调用方和遗漏的边界；没有新改动或未解疑点时，不重复执行同一批检查。
- 权限、并发、数据迁移、已上线接口兼容性等关键改动，完成实现后委派一个独立 Review 子 Agent；只报告有证据的缺陷、影响和位置，由主 Agent 修复并复验。
- 普通改动由主 Agent 自审；独立 Review 不等于再做一遍实现，也不替代测试。不能启动子 Agent 时明确说明，完成自审并报告剩余验证限制。
- 最终回复说明结果、验证结论和未完成事项，区分实际执行的检查与建议用户执行的检查。

## 规划、委派与上下文

- 简单任务使用单 Agent；多步骤任务先给简短计划，然后继续执行，不把计划本身当作交付。
- 复杂任务中有可独立开展的探索、验证或实现工作时，按需委派子 Agent；没有可独立工作的部分时保持单 Agent。
- 委派时给出明确问题、必要上下文、文件边界和输出要求；子 Agent 返回结论与文件依据，主 Agent 负责整合和最终验证。
- 默认由主 Agent 写代码，优先并行只读工作；并行实现必须隔离工作目录或分配互不重叠的文件，不让多个 Agent 同时修改同一文件。
- 优先搜索符号和相关路径，再定向读取；限制命令输出，避免把整仓库、长日志或无关文件塞入上下文。
- 同一目标继续现有会话，独立目标新开会话；长任务保留需求、已确认决策、验证结果和剩余工作，不维护与任务无关的过程文档。
- Skills 只用于匹配的专项流程，按需读取；不要把全局工程原则复制成 Skill，也不要为普通任务加载全部 Skills。

## 代码风格
- 新增 JavaScript/TypeScript 函数有多个参数时，优先用对象解构（named parameters）：`function foo({ a, b })`；框架签名、已有公共接口和项目惯例优先。
- 新文件默认按 imports → 常量 → 函数 → exports 组织，上层函数在前、辅助函数随后；通用方法的提取遵循上方简单优先原则，位置沿用项目约定。
- 命名沿用项目业务术语，表达对象、动作和用途；涉及金额、时间等值时明确单位，避免用 `data`、`result`、`helper`、`manager` 等泛名掩盖职责，也不堆砌无助理解的长名字。
- **package.json 依赖用确切版本**（如 `"2.30.0"`），不带 `^` 或 `~`。

## 注释

### 1. 核心原则：解释「为什么」，不解释「做了什么」
- **[强约束] 严禁逐行翻译代码语法**（严禁「定义变量 x 并赋值为 1」这类）。
- 重点写：业务背景、非直觉的设计抉择、边缘情况、算法依据、外部约束（第三方的行为、平台限制）。
- 代码本身说得清的、翻官方文档能查到的，都不写。
- **写这行代码做什么，不写它相对什么变了。**「上游默认是 X」「原来的值是 Y」「显式写出来防止上游改默认」属于 commit message。

### 2. 函数 / 方法级注释
- 公共函数、类、接口使用该语言标准的结构化文档注释（JSDoc / Python Docstring 等），遵循项目惯例。
- 说明功能、实际参数与返回值，仅在存在异常契约时说明异常；不为凑齐标签写空的 `@throws`。
- 内部简单辅助函数不需要。

### 3. 行内注释
- 仅在逻辑极复杂、有历史兼容代码、或有特定坑点时添加，绝不多写一行无意义的。
- 只写职责边界，不写另一侧的实现细节——写「tab 交给 tmux」可以，写「prefix C-s」会造成跨文件耦合。
- 删掉的代码不需要注释交代，那是 git history 的事；整段只剩注释就把整段删掉。
  例外：主动关掉某个默认行为时（如一批 `no_op`）要说明为什么关，否则后来看会以为多余。

### 4. 待办与特殊标记
- 统一用大写前缀：`TODO:` 待完成的功能或后续重构、`FIXME:` 已知 bug 或边界风险、`HACK:` 为兼容性或紧急上线写的临时方案。

### 5. 排版
- **一行一句。** 不要把一个句子按列宽折成多行——每行单独看都要成立。并列内容用对齐的缩进列表，不用连续散文。
- 注释单独成行，不写在代码行尾。
- 一组同类的一行注解合并成一块，代码跟在下面；不要一行注释一行代码。
- 注释紧挨它描述的那段代码，不要隔着别的语句。
- 一个文件内首字母大小写与句末标点保持一致；以标识符开头时保持原样，不要为了句式大写它。

### 6. 语言
- 默认中文，技术专有名词保留英文；语言简练直接，不写客套话。
- 已有文件跟随其现有语言，一个文件内不混用。

## 写进仓库的文件
- 内容必须对任何机器成立。「我这台现在是什么」是观察，不是事实。
- 需要指路径 / 取值时写获取方法（`git config --get`、环境变量、`$(command)`），不写字面值。
- 提交前 grep 一遍暂存区：绝对路径（`/Users/`、`/home/`）、主机名、「本机 / 这台 / 当前是」、装在本机的软件版本号。

## Git
- 写 commit message 前先读一遍模板：路径用 `git config --get commit.template` 取，按模板里的约定写。不要凭记忆。
- **署名尾行（`Co-Authored-By`）每次提交前主动问**，不要自己决定加或不加，也不要沿用其他代理的署名。

## 安全
- **不读取密钥 / 证书文件**：私钥、证书、各类服务商凭证。需要时只看目录结构或 README，不用 Read / cat / grep 碰内容。
- 不读取 `.env`、`.env.*`、`.envrc`、`secrets/`、`*.pem`、`*.key`、`id_rsa*`、`.npmrc`、`.netrc`、`.git-credentials` 及用户目录中的云服务、SSH、Kubernetes、Docker、GitHub 和代理认证文件。需要配置结构时查看示例文件或 README；不能通过 shell、脚本或其他工具绕过。
- 不运行 `sudo` 或 `git rebase`。执行 `git push` 或创建 PR 前先取得用户对该动作的明确授权。
- 默认简洁回复。

## 并发安全（读-改-写禁令）
- 库存 / 计数器 / 余额等**并发敏感字段**的写入，必须用数据库层的**原子操作**：带条件的 update，把「够不够」写进条件里。
- 禁止「先读出值 → 算新值 → 写回」的三段式。检查与使用之间存在 TOCTOU 窗口，会超卖、双花、丢计数。
- 预读只能用来优化错误提示（区分「不存在」和「不足」），不能作为正确性依据。真正的判断放在那次原子 update 的条件里，靠受影响的记录数判成功。
- 跨表 / 跨集合协同（如归还库存：扣 A → 加 B）必须先原子扣 A、成功后再操作 B，不能反过来。

## 时区
- 服务端日期逻辑，**输入（读当前时间）和输出（转换/存储）两端都要显式处理时区**。
- 不要假设进程读到的当前时间就是业务时区，先转成业务时区再做日期运算。
- 「服务器时区 = 业务时区」是巧合不是保证。

## 已上线接口的向后兼容
- 改**已上线**的接口时，**默认行为不能变**——旧版客户端仍在用户设备上运行，不会传新参数。加新能力要用纯增量：保留原默认值和原有分支，新增一个显式取值来开新逻辑。

## 可选的私有技术栈规则

处理腾讯 CloudBase 或微信/支付宝小程序项目时，先检查 `~/.codex/cloudbase.md` 是否存在；存在则读取并遵守。
这是要求代理主动读取文件的指令，不依赖 Markdown 自动导入。
该文件不存在时继续按通用原则工作，不要求安装私有仓库。
私有规则只适用于其声明的技术栈，内容不得复制进公开仓库。
